## 一句话到三分钟：项目在做什么

**一句话**：一个基于 RAG 的 AI 简历分析系统，用户上传简历后可以用自然语言提问。

**再展开一层**：它解决的是 HR 筛简历的痛点——想找「有微服务经验的候选人」，传统关键词搜索匹配不到简历里写的「Kafka + Zookeeper」，而 RAG 的语义匹配能跨越这层词汇鸿沟。

**完整架构**是四层加一层可观测性：

- **前端层**：React 19，SSE 流式渲染
- **后端层**：FastAPI，JWT 双 token 认证
- **AI 核心层**：LangGraph 状态机 + Reflexion 自纠正
- **数据层**：MySQL + ChromaDB
- **可观测性层**：Prometheus + Grafana

核心能力是 **Agentic RAG**：用 LangGraph StateGraph 把「检索 → 生成 → 评估 → 自纠正」编排成一张有向图。检索用混合策略（稠密向量 + BM25 关键词，经 RRF 融合做粗排，Cross-Encoder 做精排 20→5），带拒答门控防幻觉；答案不达标时由 LLM-as-Judge 触发 Reflexion 循环，分析失败原因后重新检索。此外集成了 MCP 协议，让任意 AI Agent 都能通过标准化工具接口来搜索简历。

## 关键技术决策：为什么是这个，不是那个

技术选型的价值不在"用了什么"，而在"为什么不用另一个"。下面几个决策是整个系统里最值得说清的。

### 为什么用 LangGraph 而不是 LangChain Agent

LangChain Agent 本质是黑盒——你不知道 Agent 下一步会调用什么工具，难调试、难测试，还可能在已经找到答案的情况下又去调另一个工具。LangGraph 的 StateGraph 是白盒：每个节点显式定义，条件边由开发者控制，State 流动清晰可追踪。

核心诉求是**可控**。简历问答是事实性任务，需要确定性而不是 Agent 的自由发挥。另外 LangGraph 内置 Checkpoint——每个节点执行完会序列化 state，支持断点恢复，这在长时间 DAG 执行时价值很大（配置见 `graph.py:35-52` 的 `checkpointer`）。

打个比方：LangChain Agent 像让实习生自由发挥，LangGraph 像给他一份 SOP。对确定性任务，SOP 比自由发挥可靠得多。

### Reflexion 与简单重试的本质区别

简单重试用相同查询再搜一次，结果大概率相同——纯粹浪费 LLM 调用。Reflexion 是**质变而非量变**：它先分析失败原因，再生成针对性的补充查询。

失败原因分三个维度评估：

- **完整性**：答案是否遗漏了重要方面（`reflection.py:91-94`）
- **准确性**：事实是否有误（`reflection.py:96-100`）
- **来源可信度**：答案是否基于检索到的文档（`reflection.py:102-106`）

举例：如果判定"答案太短、没提项目时间线"，就会生成新查询「项目工期 开始日期」再检索一轮。关键设计是 search_round ≤ 2（`graph.py:60-61`）——实验验证 2 轮最优，第 3 轮边际收益递减。

### 为什么用 MCP 而不是 REST

这不是替代关系，而是互补：REST 给前端用，MCP 给 AI Agent 用。MCP 作为 AI Agent 工具交互的标准化协议，核心价值有三点：

1. **运行时发现**：Agent 通过 `tools/list` 就知道有哪 5 个工具，不需要看 API 文档
2. **标准化参数**：JSON-RPC 2.0 的 params 结构，Agent 可直接推断参数
3. **资源 URI**：`resume://list` 等标准化地址

这是**协议层的思考**——和 REST vs GraphQL 的取舍逻辑一样，关键在于接口的消费者是谁。

### 为什么同时保留传统 RAG 和 Agentic RAG 两条流水线

两个原因。一是**速度 vs 质量**：传统 RAG 一次检索 + 生成，延迟约 4s；Agentic RAG 走 9 节点 DAG 外加可能的 2 轮 Reflexion，延迟约 10s。简单问题不值得走完整流程。二是**容错**：如果 LangGraph 依赖的某个组件出问题（如 Checkpoint 序列化失败），传统 RAG 仍然可用——系统设计的一个原则就是**核心功能不依赖非核心组件**。

用户可通过 `mode=simple` 选择传统模式。实测传统模式 p50=4.1s，Agentic p50=8.5s，但 Agentic 的 Bad Case 率低 15 个百分点。

### 混合检索：两路召回如何不重复，RRF 的 k 为什么取 100

两路召回可能返回相同文档，RRF（Reciprocal Rank Fusion）天然处理重复——同一文档在两路中的 rank 取倒数求和，自然比只在一路命中的分数高。

k=100 是参数调优实验得出的：k 越小，低排名文档的融合分数衰减越快（高排名占绝对主导）；k 越大，低排名文档贡献越多。实验发现 k=100 在 recall@5 上最优（`rag_service.py:110-120` 的 `rrf` 函数）。

### Cross-Encoder 精排：多一步为什么反而降延迟

表面上 rerank（20→5）是多了一步，但它让进入 LLM 的候选文档从 20 减到 5，prompt token 减少约 75%。LLM 调用成本远高于 rerank，本质是**用 Cross-Encoder 的微小开销换 LLM 的巨额节省**。

为什么不更激进地做 20→2？精度损失太大。实验验证 20→5 是最优平衡点（`rag_service.py:180-185` 的 `RERANK_FINAL_TOP_K`）。另一个实践发现：LLM rerank 不如模型 rerank 稳定，所以 RAG 流水线走模型 rerank，MCP tool 才走 LLM rerank。

### MCP 认证：为什么不在 FastAPI 层统一处理

MCP Server 被 mount 为 FastAPI 的子应用，有自己独立的中间件链——FastAPI 的 `AuthMiddleware` 不会应用到 `/mcp` 路径。因此单独实现了 `MCPAuthMiddleware`（`server.py:38-94`）：只拦截 `/mcp` 路径，校验 Bearer 头，decode_token 后检查 `type=access`、提取 `sub` 作为 user_id，再用 ContextVar 注入，所有 Tool 通过 `get_current_user_id()` 获取。

两个设计细节：ContextVar 不给默认值——认证失败应抛异常阻断，而不是返回无效 ID；reset 放在 finally 块防止请求间的状态污染。

## 三次真实事故复盘

做项目真正的收获往往在踩坑里。这个项目最值得记录的是三次事故。

### 事故一：ChromaDB 同步调用阻塞事件循环

ChromaDB 的 Python SDK 是同步的，在 async 视图里直接 `await chroma.query()` 会阻塞整个事件循环。解决办法是用 `asyncio.to_thread` 把它放到线程池执行（`rag_service.py:42-45`）。这也是后来反思"如果重做会换 Qdrant"的直接原因——原生异步能省掉一堆 `to_thread` 样板。

### 事故二：多参数交互效应

单参数实验里 temperature=0.1 表现最好，但组合验证后最优值变成了 0.3——因为 temperature 和 chunk_size 之间存在交互效应。这正是参数调优必须从「单参数 → 多参数 → 组合验证」逐级推进的原因（对应 07 笔记的 6 阶段实验框架）。教训是：单参数最优的简单叠加，往往不是全局最优。

### 事故三：混合检索串行转并发

最初 Dense + Sparse 两路检索是顺序执行的，p95 延迟高达 13.7s。改用 `asyncio.gather` 让两路并行，p95 延迟降了 25.5%（`rag_service.py:80-90`）。这是一个典型的"结构不变、并发方式改一下就见效"的优化。

## 两个对抗性技术疑问

有两个问题经常被拿来质疑 RAG 项目的含金量，这里正面回应。

### "这不就是调个 API 吗？"

调 API 是最后一步，只占约 5% 的代码量。真正的工作量在于：

- **检索策略**：混合检索（Dense + Sparse）+ RRF(k=100 调优) + Cross-Encoder 精排（`rag_service.py:80-200`）
- **质量控制**：LLM-as-Judge 三维评分 + Reflexion 自纠正循环 + 拒答门控
- **韧性工程**：指数退避 + NON_RETRYABLE 分类 + fallback 链 3 级（`core/retry.py` + 8 个调用点）
- **参数工程化**：6 阶段实验框架 + 120 条 golden set + LLM-as-Judge 自动评估（`rag_tuning/evaluate.py`，688 行）
- **协议拓展**：MCP 标准化 + JWT 认证 + Streamable HTTP（`mcp_server/`，700+ 行）

如果只是调 API，不会需要 5000 行后端代码和 326 个测试。

### "用 LLM 评估 LLM，不是自己夸自己吗？"

这个质疑是成立的——同一个 LLM 评估自己确实有自洽性偏差，它更倾向于认可自己生成的结论。缓解措施有几层：

1. **生成者与评估者用不同参数**：generate 用 temperature=0.3（要创造性），evaluate 用 temperature=0.0（要确定性）
2. **三维度评分**（完整性 / 准确性 / 可信度）而非单一分数，让评估更有结构
3. **实验佐证**：评估驱动的调优把 Bad Case 率从 21.7% 降到 15%，且人工抽检 20 条，评分一致性达 85%
4. **改进方向**：后续引入 RAGAS + DeepEval 标准框架，用行业通用指标做补充

关键不是"承认有局限"，而是同时说清楚为缓解局限已经做了什么。

## 模型选型：为什么是 DeepSeek

模型选型做过一轮系统对比，从成本、质量（JSON 遵循度、中文理解、推理深度）、速度三个维度评估。

**候选模型价格对比**

| 模型 | 输入价 (元/M tokens) | 输出价 (元/M tokens) | 定位 |
|------|---------------------|---------------------|------|
| **DeepSeek-V4-Pro** | 3 | 6 | 旗舰，最强能力 |
| **DeepSeek-V4-Flash** | 1 | 2 | 极致性价比 |
| **小米 MiMo-V2.5-Pro** | 3 | 6 | 高性能对标 |
| **智谱 GLM-4.5-Air** | 0.8 | 2 | 输入最低价 |
| **豆包 2.1 Pro** | 6 | 30 | 复杂任务，但贵 |

**分阶段策略**

| 阶段 | 用什么 | 为什么 |
|------|--------|--------|
| 开发调试 | DeepSeek-V4-Flash | 便宜 3 倍，快速迭代 |
| 参数调优测试 | DeepSeek-V4-Flash | 成本敏感，2M tokens 只需 ¥2.4 |
| 最终质量验证 | DeepSeek-V4-Pro | 确认质量天花板 |
| 演示 | DeepSeek-V4-Pro | 最佳生成质量 |

最终选 DeepSeek V4 系列的决定性理由是 **JSON 遵循度最好**——rerank 打分和 Agent 工具调用都强依赖结构化 JSON 输出。测试阶段用 Flash 版省约 67% 成本，最终演示用 Pro 版保证质量上限。

## 不足与改进方向

诚实地看，这个项目有三个明显短板：

1. **golden set 只有 120 条**，覆盖面有限，计划扩展到 500+ 并增加多样性
2. **未接入 RAGAS / DeepEval 标准评估框架**，自研 LLM-as-Judge 可能引入评估偏差
3. **多轮对话未实现**，当前只支持单轮问答；后续计划用 Redis 做会话缓存，结合对话摘要与指代消解

如果重做，会做两件事不一样：一是**更早固化实验框架**——参数调优在开发后期才做，若能更早定下 golden set 和实验流程，很多开发决策会更有依据；二是**向量库换 Qdrant**——ChromaDB 开发体验好，但同步 API 逼出了大量 `asyncio.to_thread` 封装，换原生异步的 Qdrant 能省约 50 行样板。
