# 评估框架的两个生产级 Bug 复盘

> 做大规模 RAG 评估时踩过两个印象最深的坑：一个是并发把连接池打爆导致进程崩溃，另一个更隐蔽——并发竞态静默污染了索引数据。前者是稳定性问题，后者是正确性问题，后者更值钱。这篇把两次事故的现象、根因、解法完整记录下来。

---

## Bug 1：连接池雪崩（稳定性 / 限流类）

**现象**：跑 P0 参数扫描（19 组 × 64 条 × 3 次 Judge ≈ 3648 次调用）时，为了降噪，给每个样本用 3 次 Judge 取中位数。结果 3 × 4 路并发 = 12 路请求同时打向 DeepSeek，连接池被打爆，疯狂报 Connection error，最后进程直接崩溃。

**根因**：这是一个典型的"并发乘积"问题——真实并发数 = 管线并发 × n_runs。表面上看每层并发都不高，但两层相乘之后瞬时并发远超连接池和 API 配额的承受力。

**解法**：

1. 用全局 asyncio 信号量把 Judge 并发锁到 6，从源头限制真实并发
2. 客户端配置 timeout 120 + max_retries 5 做兜底
3. 修复后吞吐从 4 样本/分提升到 22 样本/分

**常见误区**：只是"把并发调小"是盲调——治标不治本。真正的根治是识别出并发乘积的乘法关系，并用信号量在全局维度上设硬上限。

---

## Bug 2：并发索引竞态（正确性 / 并发安全类）

**现象**：这个 Bug 比崩溃更可怕——它**静默污染数据**，不报错。评估调度器用 asyncio 并发跑同阶段的多组参数，但同阶段的多组共用了同一个 Chroma collection 名。重建索引的逻辑是"检查是否建过 → 删除重建 → 标记建过"，这三步不是原子操作。多个协程同时冲进来，把同一个 collection 删了又建，导致索引 corruption，检索返回垃圾，幻觉率（hallucination_rate）从 0.0156 飙到 0.42。

**根因**：非原子的"检查—删除—重建—标记"序列 + 多协程共享同一 collection 名 = 经典的 check-then-act 竞态。

**解法**：

1. 用"按 collection 名维度"的 asyncio.Lock 把整段逻辑变成原子操作
2. 权衡"全局锁 vs 按名锁"——按名锁不会误伤本可并行的其他组，粒度更细
3. 把 hallucination_rate 暴涨 26× 当作报警信号，用三角印证锁定是索引 corruption 而非模型问题
4. 核心教训：**污染比崩溃更可怕**，评估系统要主动盯反常维度，而不是只看状态码

**常见误区**：直接"加一把大锁"能修复，但会无谓拖垮整体并发，也没有体现对冲突粒度的思考。锁的粒度选择本身就是设计的一部分。

---

## 为什么这两个 Bug 值得复盘

- **连接池雪崩** 属于稳定性 / 限流维度，核心是"并发预算"的工程意识——多层并发相乘时要有全局视角。
- **索引竞态** 属于正确性 / 并发安全维度，核心是能从"反常数据"反推"底层 corruption"，而不是只看状态码是否 200。
- 两个合起来，指向同一种能力：能端到端跑真实的大规模评估，并在出事时靠数据取证、定位根因。这正是 RAG / Agent 方向最需要的工程深度。
