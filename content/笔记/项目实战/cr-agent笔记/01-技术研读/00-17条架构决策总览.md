> **关联**: cr-agent-项目计划书（外部文档） | Obsidian 笔记 1-4 | 开发日志第一期到第七期

## 决策 1: Supervisor-Worker 架构（不用 CrewAI / AutoGen）

### 为什么

多 Agent 编排有四种主流模式：Supervisor-Worker、Hierarchical、Network、Sequential Pipeline。代码审查天然适合 Supervisor-Worker——一个 Supervisor 拆任务，多个专业 Worker 并行审查，最后聚合。

### 为什么不用 CrewAI

| 维度 | CrewAI | LangGraph StateGraph（我的选择） |
|------|--------|------|
| 透明度 | 黑盒（`crew.kickoff()` 一调用，内部不可控） | 全透明（StateGraph 每步显式） |
| 并发控制 | 框架决定 | 我决定（条件路由返回 list = fan-out） |
| 状态管理 | 框架内部 | SupervisorState 9 字段 + 2 个 reducer |
| 可讲性 | "CrewAI 帮我做了" | "我设计了条件路由 + reducer 合并" |

### 为什么不用 AutoGen

AutoGen 偏**对话式**（Agent 互聊），代码审查是**流水线式**（拆任务→并行→聚合），不需要 Agent 对话。

### 架构图

```text
START → decompose → [条件路由] → 4 Worker fan-out → aggregate → END
                        ↓
                   熔断 → aggregate（跳过 Workers）
```

## 决策 2: LangGraph StateGraph + Annotated Reducer

### 为什么

LangGraph 的 StateGraph 是**有向图编排**——节点是函数，边是路由，状态是共享的 TypedDict。比 LangChain 的 LCEL chain 更灵活（支持条件路由、并行、循环）。

### 关键设计：reducer 字段

```python
class SupervisorState(TypedDict):
    worker_results: Annotated[list, operator.add]  # 4 Worker 并行写入，累加不覆盖
    errors: Annotated[list, operator.add]          # 同上（踩坑后补的）
```

普通 list 字段在并发分支里会被后写者覆盖。`Annotated[list, operator.add]` 让 LangGraph 用 add reducer 累加所有分支的结果。

### 踩坑

`errors` 一开始没加 reducer，4 Worker 并发降级时只有最后一个 Worker 的错误存活。单 Worker 测试不暴露，4 Worker 并发才触发。

## 决策 3: Template Method 模式设计 Worker

### 为什么

4 个 Worker（Quality/Security/Performance/Structure）的主流程完全一样：build prompt → call LLM → parse JSON。只有 `role` 和 `system_prompt` 不同。

### 设计

```python
class BaseWorker(ABC):
    role: str = ""
    system_prompt: str = ""

    async def review(self, code, language):
        # Template Method：build → call → parse（子类不重写）
        prompt = self._build_prompt(code, language)
        text = await asyncio.wait_for(self._call_llm(prompt), timeout=self.timeout)
        return self._parse_response(text)
```

子类只需 2 行：

```python
class SecurityWorker(BaseWorker):
    role = "security"
    system_prompt = "你是安全审查专家..."
```

### 为什么不用 @abstractmethod

ABC 的 `@abstractmethod` 阻止实例化但不阻止子类不实现。我用 `__init_subclass__` 在**类定义时**校验 `role` 和 `system_prompt` 非空——漏设立即 TypeError，不用等运行时。

## 决策 4: 三层容错（熔断 + 超时 + 异常不阻塞）

### 为什么

LLM 是概率性服务——可能超时、返回乱码、拒绝回答。多 Agent 系统里，一个 Worker 挂了不能让整个 graph 崩。

### 三层设计

| 层级 | 防什么 | 机制 | 降级动作 |
|------|--------|------|----------|
| 熔断 | 死循环 | iteration_count + 条件边 | 跳过 Workers → aggregate |
| 超时 | LLM 卡死 | asyncio.wait_for(120s) | 降级 info finding |
| 异常不阻塞 | Worker 崩溃 | try/except + errors reducer | 降级 finding + 记录 errors |

### 关键：timeout 可注入

```python
class BaseWorker(ABC):
    timeout: float = 120.0  # 生产 120s，测试覆写 0.01s
```

测试超时路径时不可能等 120 秒——覆写为 0.01s 验证降级逻辑。

## 决策 5: 同步 API（第一版）→ 异步 API（第二版）

### 为什么

第一版没有任务队列（Celery/Redis），同步执行最简——POST 直接返回 completed + report。第二版加 Celery 后改 202 + 后台异步，API contract 不变，前端不用改。

### 设计

```python
@router.post("/reviews")
async def create_review(req: ReviewRequest, db=Depends(get_db)):
    # W1: 同步执行 graph
    graph = build_supervisor_graph()
    result = await graph.ainvoke({"code": req.code, ...})
    # 直接返回 completed
    return ReviewResponse(status="completed", report=result["report"])
```

### 演进路径

第二版改为 `BackgroundTasks` + 202 + `pending/running/completed` 状态机。接口契约不变。

## 决策 6: 数据层两层分离（ORM vs Pydantic）

### 为什么

`models/` 是 SQLAlchemy ORM（数据库持久化），`schemas/` 是 Pydantic（API 边界校验）。两层分离避免 ORM 对象直接暴露给 API。

### 关键坑

`ReviewTask.findings` 用 SQLAlchemy `JSON` 类型（不是 `Text`），否则读回来是字符串不是 list。

## 决策 7: 依赖注入 + 模块引用（测试可 mock）

### 为什么

Worker/Decompose 接收可选的 LLM client，测试时注入 mock client。生产代码用 `from backend.core import llm as llm_mod; llm_mod.get_chat_client()`——模块引用而不是函数引用。

### 踩坑

`from module import func` 是值拷贝——monkeypatch 源模块不影响已导入的引用。改成 `import module; module.func()` 后 monkeypatch 才生效。

## 决策 8: pytest.ini 而非 pyproject.toml

### 为什么

pytest-asyncio 的 `asyncio_mode=auto` 在 `pyproject.toml` 的 `[tool.pytest.ini_options]` 里**不稳定**——通过 `testpaths` 调用时读不到，导致 async 测试被 STRICT 模式 skip。

### 解法

用独立的 `pytest.ini` 文件，pytest-core 和 pytest-asyncio 都稳定读取。

```ini
[pytest]
asyncio_mode = auto
testpaths = backend/tests
```

## 决策 9: .env 绝对路径加载

### 为什么

pydantic-settings 的 `env_file` 是 CWD-relative，不是 module-relative。从项目根运行找不到 `backend/.env`。

_BACKEND_DIR = Path(__file__).resolve().parent.parent

双层加载：`.env`（通用）→ `.env.dev`（环境特定，覆盖前者）。

## 决策 10: Aggregator 去重 key = (line, description_lower)

### 为什么

4 个 Worker 可能发现同一个问题（比如 Security 和 Performance 都标了第 10 行）。去重 key 用 `(line, description_lower)`——行号相同 + 描述相似视为同一条。

### 设计

```python
def aggregate_findings(findings: list[dict]) -> list[dict]:
    seen = set()
    deduped = []
    for f in findings:
        key = (f.get("line"), f.get("description", "").lower()[:50])
        if key not in seen:
            seen.add(key)
            deduped.append(f)
    return sorted(deduped, key=lambda x: SEVERITY_ORDER.get(x["severity"], 99))
```

severity 排序：high → medium → low → info。

## 决策 11: MCP Gateway 用独立 FastMCP 包（不用官方 SDK 内置）

### 为什么

MCP 把"工具调用"标准化成 JSON-RPC 2.0 接口，让外部客户端（Claude Desktop / Cursor / 自研前端）用同一协议调我的审查引擎。FastMCP 是社区维护的上层封装，比官方 `mcp.server.fastmcp` 更新快、功能全（自带 Starlette ASGI app、resource/tool 装饰器、streamable-http 传输）。

### 设计

```python
from fastmcp import FastMCP
mcp = FastMCP("cr-agent")
@mcp.tool()
async def review_code(code: str, language: str) -> str:
    graph = build_supervisor_graph()
    result = await graph.ainvoke({"code": code, "language": language})
    return result["report"]
mcp_app = mcp.http_app(transport="streamable-http", stateless_http=True, path="/")
```

Tool 内部调第一版的 `build_supervisor_graph().ainvoke()`——**MCP 是壳，引擎是核**，零逻辑重复。

### 为什么不用官方 SDK 内置

`from mcp.server.fastmcp import FastMCP` 也能用，但 FastMCP 独立包 `pip install fastmcp` 是单独演进的项目，文档/示例更友好，W1 的 ai-resume-analyzer 已用过，降低认知负担。

## 决策 12: GitHub 集成用 `.patch` 纯文本格式（不用 REST API）

### 为什么

拉 PR diff 有两条路：

| 方式 | 优点 | 缺点 |
|------|------|------|
| GitHub REST `pulls/{n}/files` | 结构化 JSON | 需 token、有速率限制、要解析 base/head |
| `.patch` 纯文本 | 免 token、不限速、diff 直观 | 需自己解析 hunk |

选 `.patch`：`https://patch-diff.githubusercontent.com/raw/{owner}/{repo}/pull/{number}.patch`。不用认证即可拉公开仓库 PR，本地解析 hunk 行首 `+`/`-`/` ` 即可。

### 解析设计

```python
def parse_patch_to_code(patch: str) -> str:
    # 保留 + 新增行 + 上下文行（去前导空格），丢 - 删除行
    # 每段加 # File: <path> 分隔，让 LLM 知道在看哪个文件
```

只保留 `+` 与上下文行——删 `-` 删除行（不会引入新问题的旧代码），但**必须保留上下文行**，否则 `API_KEY = "sk-xxx"` 这类未改动但关键的上下文会消失，审查会变盲。

## 决策 13: MCP sub-app 挂载到 FastAPI 的 ASGI 语义

### 为什么

`app.mount("/mcp", sub_app)` 是 ASGI 原语——它**剥离 `/mcp` 前缀**再把剩余路径转发给 sub_app。sub_app 内部路由必须基于"根"设计。

### 两个坑

1. **双前缀 404**：`http_app()` 默认内部路由 `/mcp`，mount 剥离 `/mcp` 后变成 `/mcp/mcp/` → 404。→ `http_app(path="/")` 让内部路由在根，剥离后正好 `/mcp`。
2. **lifespan 不触发**：mounted sub-app 的 lifespan 不随父 app 自动跑（报 `Task group is not initialized`）。→ FastAPI lifespan 里手动 `async with _mcp_app.router.lifespan_context(_mcp_app)`；测试用 `asgi-lifespan` 的 `LifespanManager` 单独触发。

### 教训

ASGI mount ≠ HTTP redirect，前缀剥离是框架行为，子 app 路由要配合"根路径"设计；sub-app 的启动逻辑要手动串进父 app 的 lifespan。

## 决策 14: LLM-as-Judge 评测体系（对齐 1 号项目）

### 为什么

Agent 评测是 R0 知识点（成本控制 / Agent 评测 / LLM-as-Judge）。要证明 cr-agent 的审查质量，不能只靠"跑通"，要有量化评分。

### 三维度（对齐 ai-resume-analyzer）

```python
_composite = 0.4 * completeness + 0.4 * accuracy + 0.2 * source_traceability
```

- completeness：是否覆盖全部 expected_findings
- accuracy：报告里的 finding 是否真有问题（不误报）
- source_traceability：finding 是否指向具体行/文件

### 双评分模式

| 模式 | 用途 | 约束 |
|------|------|------|
| rule-based | CI 基线、无 LLM 依赖 | 确定性，只比 expected vs actual 覆盖 |
| LLM judge | 高质量、语义级评分 | client 可注入，必须 `await` |

`_parse_judge_json` 去 JSON 代码围栏 + 正则兜底，避免 LLM 输出格式漂移导致 `json.loads` 失败。

### 真实数据

24 条评测集（四维度均衡），`--limit 3` 真实跑 → composite_avg=1.0（sec-001/002/003 全满分）。

## 决策 15: 评测用「软硬双指标」——LLM-as-Judge + PRF

### 为什么

第二版的 LLM-as-Judge 是「软指标」——裁判本身也是 LLM，有方差、有成本、受 prompt 影响。只靠它证明"质量好"不够可信。

必须加「硬指标」：**precision/recall/F1**，用 ground truth（expected_findings）和实际发现比对，确定性、可复现。两个指标交叉验证，才敢说"审查质量好"。

### 怎么比（compute_prf）

```python
def _key(f): return (f["description"][:10].lower(), f.get("line"))
# expected / actual 各抽象成 key 列表，贪心一对一匹配：
#   TP = expected 命中 actual；FN = expected 未命中；FP = actual 未命中
#   precision = TP/(TP+FP)；recall = TP/(TP+FN)；f1 = 2PR/(P+R)
```

空集约定：expected 空 → precision=recall=f1=1.0（无 ground truth 不扣分）；actual 空 → recall=0、precision=1.0。

### 关键坑

`run_one` 一开始返回 **reducer 累加的原始** worker_results（4 Worker × N findings = 重复），直接算 PRF 会把重复 finding 算成 FP，precision 暴跌到 0.2。→ 先 `aggregate_findings()` 去重，用和报告一致的 findings 算 PRF。

### 评测的价值在「回归对比」

judge 的绝对值受裁判模型影响，**相对变化**（改 prompt 后 composite 从 0.8→0.9）才可信。PRF 提供不依赖裁判的硬基准。

## 决策 16: 成本控制用 TokenMeter 包 client（不侵入 Worker）

### 为什么

课程中的「成本控制」知识点，前两周开发时都没落地——不计量就不知道"一次审查花多少 token / 多少钱"，无法做优化、无法给讲量化数据。MCP Gateway（决策 2）的论点是「统一入口可观测」，这里把可观测落到 token 级。

### 设计（MeteredClient 代理模式）

```python
class MeteredClient:
    def __init__(self, real, meter): self._real, self._meter = real, meter
    @property
    def chat(self): return _MeteredChat(self._real.chat, self._meter)
    def __getattr__(self, name): return getattr(self._real, name)  # 其余属性代理

class _MeteredCompletions:
    @property
    def create(self):
        async def _metered(*a, **k):
            resp = await self._real.create(*a, **k)
            if getattr(resp, "usage", None): self._meter.add(resp.usage)
            return resp
        return _metered
```

只拦截 `.chat.completions.create` 这一个调用路径（graph / judge 都走它），**不侵入 Worker 代码**——`MeteredClient` 代理其余属性/方法到真实 client。

### 接入方式

`run_one(meter=None)`：传入 meter 时，临时 monkeypatch `llm_mod.get_chat_client` 返回 `MeteredClient(real, meter)`，graph 跑完还原。`estimate_cost(meter, 单价)` 按 ¥/1k tokens 出成本。当前模型免费 → 成本 0，但计量框架就位，换收费模型直接出数。

### 为什么不用侵入式埋点

在 Worker 里加 `meter.add(...)` 要改 4 个 Worker + decompose 的代码，且和 graph 耦合。代理模式在边界（client）一处拦截，零侵入、可测试（fake client 返回 usage 即可验）。

## 决策 17: 评测 CLI 的 token 计量开关 + 模块函数还原（第三版收尾补丁）

### 背景

第三版开发过程中我写了 `TokenMeter` + `MeteredClient`（决策 16），但收尾时回头检查发现：`run_all(dataset, limit, meter=None)` 的 `meter` 只在显式传入时才计费，而 `main()` 调的是 `run_all(args.dataset, args.limit)`——**漏传 meter**。结果真实跑 26 样本时 `summary["tokens"]` 永远 `None`，成本数据拿不到。这是"功能写了但默认不接"的典型坑。

### 决策

1. **CLI 加 `--tokens` 开关**：`main()` 创建 `TokenMeter`，透传 `run_all(..., meter=meter)`。meter 激活后 `llm_mod.get_chat_client` 被 `MeteredClient` 替换，`judge_with_llm(client=None)` 也走它 → graph + judge 全量 token 都被计入。
2. **还原存函数引用不存实例**：`run_one` 临时 monkeypatch 全局时，进入前 `original_getter = llm_mod.get_chat_client` 存**函数本身**，finally 还原 `llm_mod.get_chat_client = original_getter`，而非 `lambda: real`（具体实例）——后者会覆盖测试的 monkeypatch，造成测试间状态泄漏。

### 为什么

- `--tokens` 默认关：日常评测只关心质量（composite/PRF），不想每次都走真实 LLM 计 token；需要成本数据时才显式开。
- 还原函数引用：这是 Python 可测试性的细节坑（模块引用调用 vs 值拷贝）。凡是"临时 monkeypatch 全局、跑完还原"的模式，还原的必须是被替换的**原对象/函数**，不是过程中的某个返回值。
