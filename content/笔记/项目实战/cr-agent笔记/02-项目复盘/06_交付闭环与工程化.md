# 交付闭环与工程化

> CLI、API、测试三条交付通道的打通之路——从 `python -m` 找不到入口，到环境变量路径"打哪指哪"，再到 120s 超时调优。

## 一、背景（为什么要做这个）

Playground 能跑只是第一步。"交付"意味着用户不依赖 IDE 也能用——CLI 可脚本化、API 可接入 CI、测试在沙箱能通过。Phase 0 定的验收标准有一条："CLI 和 API 输入/输出一致，只是从文件读取 code。"

## 二、逐个讲：问题 → 怎么想 → 怎么解

### 1. `python -m backend.cli` 报 No module → 加 `__main__.py`

**问题**：按 Python 包规范，`python -m <包>` 找的是 `__main__.py` 而不是 `main.py`。项目目录里只有 `cli/main.py`，没有 `__main__.py`，跑起来就报 "No module named backend.cli"。

**怎么想**：Python -m 机制不是"找同目录的 main.py"，而是"执行包的 `__main__.py`"。这是 CPython 37 年来的硬规则，不能绕。

**怎么解**：在 `backend/cli/` 下加 `__main__.py`，内容两行：`from .main import main; main()`。同时保留 `main.py` 做逻辑入口，`__main__.py` 只做重定向。这样既支持 `python -m backend.cli`，也支持 `python -m backend.cli.main`（调试用）。

### 2. `.env` 加载路径"打哪指哪" → `Path(__file__).resolve()` 双层加载

**问题**：`python_dotenv.load_dotenv(".env")` 默认从 CWD 加载。从项目根跑没问题，但从 scripts/ 或别的目录跑就会"漏加载"——环境变量没设上，API key 为空，LLM 调用全部崩溃。

**怎么想**：问题本质是**相对路径依赖 CWD**，CWD 不可控。正解是**基于代码位置算路径**，而不是基于调用位置。

**怎么解**：用 `Path(__file__).resolve().parents[2]` 定位项目根（代码在 `backend/core/config.py`，往父级走 2 层到项目根），然后 `load_dotenv(root / ".env")` 和 `load_dotenv(root / ".env.dev", override=True)` 双层加载——`.env` 是通用配置，`.env.dev` 覆盖敏感字段（如 API key），后者不进 git。

### 3. mimo 单次 26s，120s 超时阈值是怎么确定的

**问题**：Phase 5 初版设 30s 超时，真实调用时 4 个 Worker 全部超时——`asyncio.TimeoutError`，全都降级为 "跳过该维度审查"。mimo-v2.5 单次代码分析 ~26.5s，加上 prompt 构建 + 解析，单 Worker 实际耗时 ~30s。4 Worker 并发，有些更慢。

**怎么想**：30s 是基于"1 次 LLM 调用"的直觉预估，不是基于真实测量。应该先用真实数据测量，再设阈值。安全系数留 3x 以上。

**怎么解**：实测 mimo 单次 26.5s，4 Worker 并发最慢 ~35s，设 120s（约 3.4x 安全系数）。超时是类属性 `timeout: float = 120.0`（可注入），测试时覆写为 0.01s 即可验证超时路径，不等 120s。

### 4. 同步 API 和流式 API 代码复用 → 抽 `_create_review_record`

**问题**：同步 POST `/reviews` 和流式 POST `/reviews/stream` 都建数据库记录，逻辑 6 行完全一样，但控制流不同（return vs yield），不能强行合到一个函数。

**怎么想**：控制流不能合并，但纯数据操作可以。把"建记录"抽成 `_create_review_record()`，两个接口都调它。核心审查逻辑（graph 构建、状态恢复）也抽成公共函数。

**怎么解**：抽了 4 个公共函数——`_create_review_record()`（建库）、`_sse_event()`（SSE 格式包装）、`_is_user_node()`（节点过滤）、`_fetch_pr_code()`（PR 输入转换）。同步和流式接口各自调用这些函数，核心逻辑不重不漏。

## 三、关键决策与取舍

| 决策 | 选择 | 取舍 |
|------|------|------|
| CLI 入口结构 | `__main__.py` 重定向 `main.py` | 比合二为一多了个文件，但职责清晰——入口只做导入，逻辑在 main |
| .env 加载策略 | `Path(__file__).resolve()` 算根 + 双层加载 | 代码位置硬耦合，但换来了无论从哪启动配置都正确 |
| 超时阈值 | 120s（3.4x 实测值） | 比 30s 安全很多，但极端慢速场景可能还是超时 |
| API 同步/流式复用 | 抽公共函数，控制流分开 | 比"合到一个函数加 if"多了一点重复，但控制流清晰可读 |
| 同步端点 vs 流式端点 | 保留同步 POST 作为 fallback | 多了一份路径，但流式断了用户还能切同步 |

## 四、踩坑（值得讲的故事）

**1. `__main__.py` 缺失**

现象 → 根因 → 解法 → 教训

第一次跑 `python -m backend.cli review --file test.py`，报了 ModuleNotFoundError。查了 10 分钟才意识到 `-m` 找的是 `__main__.py` 不是 `main.py`。解法就是加两行。教训：Python 入门级知识，但实际开发容易忘——`python -m` 和 `python file.py` 的加载机制不一样。

**2. `.env` 路径谜题**

现象 → 根因 → 解法 → 教训

在 `D:\Project\cr-agent\scripts\` 下跑 `python ..\backend\cli.py`，LLM 调用报 "401 Unauthorized"。调试了半天发现 API key 是空的——`load_dotenv(".env")` 在 scripts 目录找 .env，找不到。解法：`Path(__file__).resolve()` 定位。教训：**绝对路径问题要用绝对路径解决**——文件位置是确定的，CWD 是不确定的。

**3. 30s 超时全部 Worker 降级**

现象 → 根因 → 解法 → 教训

4 个 Worker 全降级，报告为空。第一反应是代码有 bug，排查了 1 小时才发现是超时阈值不够。mimo 单次 26s + 4 并发叠加，30s 完全不够。解法：实测后设 120s。教训：**不做假设驱动，要做数据驱动**——超时阈值不是拍脑袋的，要基于真实调用测量。

## 五、常见疑问

**Q1：`python -m backend.cli` 和直接 `python backend/cli/main.py` 有什么区别？**

A：`-m` 把包路径加入 sys.path，支持相对导入（`from . import xxx`）。直接 `python backend/cli/main.py` 把 main.py 所在目录加入 sys.path，"包"的概念没了，相对导入会报 `ImportError: attempted relative import with no known parent package`。所以 CLI 入口必须用 `__main__.py` + `-m` 方式运行。

**Q2：为什么 .env 要双层加载（`.env` + `.env.dev`）？**

A：`.env` 是通用配置（MODEL、BASE_URL），进 git，团队共享。`.env.dev` 是本地敏感配置（API_KEY、SECRET），不进 git，各自维护。双层加载让通用配置在 repo 里可追踪，敏感配置不泄露。且 override=True 确保本地配置优先级更高。

**Q3：120s 超时会不会太长？用户要等 2 分钟？**
