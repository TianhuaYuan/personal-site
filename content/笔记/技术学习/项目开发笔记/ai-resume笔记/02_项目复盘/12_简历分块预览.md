# 简历分块预览

> **电梯陈述**：「新增了 `GET /api/v1/resumes/{id}/chunks` 端点 + `ChunksModal` 前端组件，让用户看到简历被  系统切成了什么块。难点是  数据不在 MySQL，存在 ChromaDB——必须用全局锁 `with_chroma` 串行化访问。」

## 一、背景

用户上传简历后只能看分析结果，看不到"简历被怎么切的"——RAG 的  策略直接决定检索质量，但对用户是黑盒。这个功能让  可解释，是项目完整度的关键一环。

## 二、逐个讲：问题 → 怎么想 → 怎么解

### 1. 数据源：ChromaDB 而非 MySQL

**问题**：chunks 数据存哪？简历表 `resumes` 只有 `chunk_count` 和 `parsed_text`，chunks 本身不在 MySQL。

**解决**：调 `collection.get(include=["documents", "metadatas"])` 从  取 chunks（document + metadata，不带  省带宽）。

### 2. 并发安全：with_chroma 全局锁

**问题**：ChromaDB 的  非线程安全——并发读写会损坏  索引（这是项目踩过的坑）。新端点也必须遵守这个约束。

**解决**：用项目中已有的 `with_chroma` 包裹同步操作：

```python
def _sync_get() -> dict | None:
    try:
        collection = get_chroma_client().get_collection(name)
    except Exception:
        return None
    return collection.get(include=["documents", "metadatas"])

data = await with_chroma(_sync_get)
```

`with_chroma` 内部：`async with _chroma_lock: await asyncio.to_thread(func)`——先抢全局锁，再扔线程池。

### 3. 双存储的归属校验

**问题**：归属校验查 MySQL，chunk 数据查 ChromaDB。怎么组织？

**方案 A**（采用）：端点先调 `resume_service.get_resume` 校验归属（ 非本人），再调 `chunks_service` 取 chunks。校验和数据查询分离，各司其职。

**方案 B**（放弃）：chunks_service 内部做校验。问题是把校验逻辑散到  层，跟现有模式不一致。

### 4.  不存在的 409

ChromaDB  不存在分两种情况：
- **简历还在 processing**：Chroma 没建好 → 返回 409 "简历未就绪"
- **数据不一致**：MySQL status=ready 但  被清过 → 同样 

方案 B（全局 409）优于方案 A（分场景 404/409）：前端只需处理两种状态（有数据/无数据），简化了错误处理。

### 5. 前端渐进式披露

 默认折叠全部块，只显示黄色高亮的字符位置摘要。用户点击某块才展开原文。为什么？
- **认知负荷**：一上来展开几十块原文会让用户不知所措
- **信息层次**：先给摘要（位置+长度），需要再看详情
- 类比：代码折叠编辑器——默认只看到函数签名，点开看实现

### 6. 单测三大坑

**坑 1：mock side_effect 误用**。一开始写 `mock_chroma_collection.get.side_effect = [valid_chunks]` 但没意识到 `collection.get()` 在 `with_chroma` 内部可能被调多次——side_effect 是依次消费列表，第二次调就报 StopIteration。改用 `return_value`。

**坑 2：正则匹配多元素**。前端测试里 `screen.getByText(/共  块/)` 匹配到多个元素（折叠时有一个，展开后又渲染一个），断言失败。改用 `getAllByText` 并显式取第一个。

**坑 3：ChunksModal 闪烁**。Modal 刚打开时还没加载 chunks，瞬间显示空内容再显示 skeleton → 视觉闪烁。用 `loading`  同步控制  状态。

## 三、关键决策

| 决策 | 选择 | 取舍 |
|------|------|------|
| 数据源 | ChromaDB（非 MySQL） | 必须用 with_chroma 锁串行化 |
| 404 vs 409 |  非本人 /  数据未就绪 | 清晰区分两种"无数据"原因 |
| 默认折叠 | 渐进式披露 | 减少认知负荷，需要多看一次 |
|  操作 | with_chroma 全局锁 | 安全但串行化；数据量小无瓶颈 |

## 四、Q&A

**Q：为什么  不在 MySQL？** —  是项目选定的向量库，chunk 文本 + metadata +  存在一起，检索时一次性取出（`collection.get`），不需要跨存储拼接。

**Q：with_chroma 会不会成瓶颈？** — 当前数据量小（单简历 chunks < 50），锁争用几乎为零。若扩展到大量并发，可按 resume_id 维度拆锁。

**Q：为什么默认折叠？** — 认知负荷原则。先给摘要，用户需要再展开细节，和信息检索的"先粗后精"思路一致。
